# Real Estate Manager

Application de gestion d'un patrimoine locatif personnel : biens/immeubles, gestionnaires, locataires, et suivi financier (loyers, impayés, dépenses, virements).

## Contexte métier

Le propriétaire possède :
- 1 appartement à Villiers-sur-Marne (loi Pinel), en **gestion locative complète** par ArthurImmo (un seul gestionnaire fait tout).
- 1 immeuble de 3 appartements à Sedan : **mise en location** par Pergent Immobilier, **gestion** (loyers, urgences, comptes-rendus) par Locagestion.
- 1 immeuble de 4 appartements à Charleville-Mézières : même répartition que Sedan.

Deux rôles de gestionnaire sont donc modélisés séparément : `mise_en_location` (recherche de locataire, états des lieux) et `gestion` (loyers, urgences, comptes-rendus). Une "gestion locative complète" se traduit simplement par un même gestionnaire portant les deux rôles sur une unité — **il n'existe pas de valeur d'enum à part pour ce cas** (voir `app/models/mandat_gestion.py`).

## Contraintes fortes (à respecter dans toute évolution)

1. **Raspberry Pi 5 (16 Go RAM, SSD, Debian Bookworm)** est la cible d'exécution. Toujours privilégier les composants légers et locaux plutôt que des alternatives lourdes (pas de moteur DB serveur séparé, pas de bundler JS, pas de queue/broker pour ce volume de données).
2. **Projet totalement indépendant** des autres projets de l'utilisateur : aucune réutilisation de code/fonction/méthode provenant d'ailleurs. Ce dépôt est autonome.
3. L'interface web doit être servie sous le path `/real-estate-manager/`. **L'application le gère nativement** (montage interne via `app.mount(ROOT_PATH, ...)`, voir `app/main.py`) — ça fonctionne donc aussi bien en accès direct (IP:port) qu'en production, sans dépendre d'un reverse proxy qui réécrirait le chemin. Le HTTPS/TLS n'est **pas** géré par cette application : il est assuré en amont par un reverse proxy mTLS tournant sur un autre Raspberry Pi — **ce proxy doit transmettre le chemin tel quel, SANS retirer le préfixe** (simple `reverse_proxy` / `proxy_pass`, pas de réécriture de chemin à configurer). L'authentification applicative reste donc un simple login/mot de passe.
4. **Pas de connexion bancaire automatique** (ni agrégateur DSP2, ni scraping) : les virements reçus sont **déclarés manuellement** par l'utilisateur via un écran dédié, avec un rapprochement assisté contre les lignes de paiement extraites des comptes-rendus PDF.
5. Les mails des gestionnaires sont lus depuis une **boîte Gmail dédiée** (pas la boîte personnelle de l'utilisateur), en **IMAP + mot de passe d'application** (pas l'API Gmail OAuth2 — en statut "Test" sur Google Cloud, les refresh tokens des scopes restreints comme `gmail.readonly` expirent au bout de 7 jours, impraticable pour un service autonome ; IMAP + mot de passe d'application n'a pas cette limite). **La boîte dédiée reçoit tout le courrier personnel transféré** (pas que les 3 gestionnaires) : impossible de filtrer par expéditeur. Le tri est donc **manuel**, pièce jointe PDF par pièce jointe, via l'écran `/ingestion-mail` (import ou "ignorer").
6. **Tous les modules de code applicatif (routers, services, logique métier) doivent avoir une couverture de tests unitaires complète** (cas heureux + cas limites/erreurs), pas seulement un test de fumée — contrairement au modèle de données initial qui n'a qu'un test illustratif. Un audit complet (`pytest-cov`) mené le 2026-10-28 a porté la couverture de 96 % à 99 % (309 → 357 tests) ; les lignes restantes non couvertes sont soit du bootstrap (`app/main.py`, `app/database.py`, `app/security.py`), soit le code structurellement mort décrit plus bas (branches `Form(...)` vide inatteignables), soit des artefacts de `coverage.py`.

## Stack technique

| Couche | Choix | Pourquoi |
|---|---|---|
| Langage | Python 3.11+ | léger à l'exécution, écosystème mature pour parsing PDF/mail |
| Backend web | FastAPI + Uvicorn | léger, async natif pour le polling mail en tâche de fond |
| ORM / modèles | SQLModel | typage propre, basé sur SQLAlchemy + Pydantic |
| Base de données | SQLite (`data/app.db`) | mono-utilisateur, zéro serveur dédié, suffisant pour ce volume |
| Migrations | Alembic (configuré, autogenerate branché sur `SQLModel.metadata`) | |
| Frontend | Jinja2 + HTMX + Alpine.js, vendorisés localement dans `app/static/js/` (pas de CDN) | pas de build JS, faible empreinte CPU/RAM sur ARM |
| Auth | Session cookie (`itsdangerous`/Starlette `SessionMiddleware`) + mots de passe hashés en Argon2 (`argon2-cffi`) | cohérent avec le TLS déjà géré en amont ; pas besoin de JWT/OAuth pour une appli mono-utilisateur |
| Scheduler | APScheduler in-process (`BackgroundScheduler`) | pas de worker/broker externe ; thread séparé car `imaplib` est bloquant |
| Notifications push | ntfy (`https://ntfy.sh`, topic dédié), requête HTTP stdlib (`urllib.request`) | zéro dépendance supplémentaire, zéro infra à gérer |
| Ingestion mail | IMAP stdlib (`imaplib`/`email`), zéro dépendance supplémentaire | pas d'API OAuth : évite l'expiration à 7 jours des refresh tokens en statut "Test" Google Cloud ; stdlib suffit, pas besoin d'`imap-tools` |
| Parsing PDF (à venir) | pdfplumber ou pymupdf, un adaptateur par gestionnaire (`app/services/extraction/`) | formats de compte-rendu différents selon ArthurImmo / Pergent / Locagestion |
| Déploiement (à venir) | systemd direct (sans Docker) | évite tout overhead de conteneur |

- [x] **Sauvegarde automatique quotidienne** (`app/services/sauvegarde.py`, ajouté le 2026-10-29) : `data/app.db` est copiée chaque jour (3h du matin par défaut, `SAUVEGARDE_DB_HEURE`) vers `data/backups/app-AAAA-MM-JJ.db`, via l'API native de backup de SQLite (`Connection.backup()`) plutôt qu'un simple `cp` — SQLite peut être en cours d'écriture (mode WAL) au moment de la copie, un `cp` brut risquerait une sauvegarde corrompue. Les sauvegardes de plus de `SAUVEGARDE_DB_NOMBRE_JOURS_CONSERVES` jours (30 par défaut) sont purgées automatiquement à chaque passage pour ne pas remplir le disque. En cas d'échec (disque plein, permissions), une **notification ntfy** part immédiatement (contrairement au scan mail qui échoue souvent pour des raisons réseau transitoires sans alerter, un échec de sauvegarde mérite d'être vu vite) — jamais de plantage du process dans les deux cas. `data/backups/` n'est pas versionné (seul `.gitkeep` l'est, même pattern que `data/documents/` et `data/credentials/`).

## Modèle de données — résumé

Voir le détail des champs directement dans `app/models/` (un fichier par entité, nommé en snake_case du nom de la classe). Schéma relationnel :

```
Bien 1──N UniteLocative N──N Gestionnaire (via MandatGestion + rôle + compte bancaire de versement)
UniteLocative 1──N Occupation N──N Locataire (via OccupationLocataire)
MandatGestion 1──1 CompteBancaire (compte propre au mandat, pas au gestionnaire)
Gestionnaire 1──N ContactGestionnaire (plusieurs emails/téléphones)
Gestionnaire 1──N ReleveGestion 1──N LignePaiement / LigneDepense
Bien/UniteLocative 1──N DepenseRecurrente 1──N LigneDepense (modèle récurrent, hors relevé)
Gestionnaire 1──N VirementRecu ──1 Rapprochement──N RapprochementLigne──(LignePaiement | LigneDepense)
```

`LigneDepense` a donc trois origines mutuellement exclusives : `releve_gestion_id` (extraite d'un compte-rendu), `depense_recurrente_id` (générée depuis un modèle récurrent), ou aucune des deux (saisie manuelle ponctuelle).

Un bien de type `appartement_isole` n'a qu'une seule `UniteLocative` ; un `immeuble` en a plusieurs. La vacance d'une unité est **dérivée** (aucune `Occupation` avec `statut = active`), jamais stockée en dur.

## Authentification

Pas d'écran d'inscription (application mono-utilisateur) : créer un compte via `scripts/creer_utilisateur.py --email ...` (mot de passe saisi en masqué via `getpass`, jamais en argument de ligne de commande). La logique réutilisable est dans `app/services/gestion_utilisateurs.py`.

Un accès non authentifié à une route protégée (dépendance `get_current_user`, `app/security.py`) lève une `HTTPException(401)`, interceptée par un handler global (`app/main.py`) qui redirige vers `/login` plutôt que de renvoyer une erreur JSON.

## Préfixe d'URL `/real-estate-manager/`

`app/main.py` définit deux objets ASGI :
- **`app`** : l'application "nue", routes sans préfixe (`/login`, `/`, `/biens`, ...). C'est elle que les tests importent et exercent directement — aucun test n'a besoin du préfixe.
- **`app_prefixee`** : `app` montée sous `ROOT_PATH` via `app_prefixee.mount(ROOT_PATH, app)`. C'est elle que `python -m app.main` (et donc le service systemd) lance réellement.

Ce montage est **natif** : Starlette gère lui-même le `root_path` à chaque requête selon le chemin réellement appelé, donc tout ce qui est généré dynamiquement (`url_for`, liens dans les templates, fichiers statiques) est automatiquement correct — en accès direct IP:port (`http://<ip>:8000/real-estate-manager/login`) comme en production derrière le reverse proxy. **Il n'y a plus de `--root-path` passé à uvicorn** (ancienne approche, abandonnée : elle supposait qu'un proxy externe retire le préfixe avant de transmettre, ce qui cassait l'accès direct sans proxy).

Conséquence pour le reverse proxy de l'autre Raspberry Pi : il doit **transmettre le chemin tel quel** (pas de réécriture/strip de préfixe à configurer — un simple passthrough suffit).

## Déploiement systemd

Le service est **installé et démarré** (`enable --now` fait le 2026-10-28). Pour le réinstaller/reconfigurer si besoin :

```bash
# 1. S'assurer que .env a APP_HOST=0.0.0.0 (ou l'IP LAN du Pi) — 127.0.0.1 par défaut
#    n'est PAS joignable depuis l'autre Raspberry Pi qui fait reverse proxy.
# 2. Vérifier que les migrations sont à jour et qu'un utilisateur existe :
.venv/bin/alembic upgrade head
.venv/bin/python scripts/creer_utilisateur.py --email moi@exemple.fr   # si pas déjà fait

# 3. Installer l'unité systemd :
sudo cp deploy/real-estate-manager.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now real-estate-manager

# Suivi :
sudo systemctl status real-estate-manager
journalctl -u real-estate-manager -f
```

Les migrations ne sont **pas** auto-appliquées au démarrage du service (volontaire — éviter qu'une migration non testée s'applique seule sur un redémarrage/crash-loop) : `alembic upgrade head` reste une étape manuelle avant chaque déploiement d'une nouvelle version.

## Commandes utiles

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"     # installation
.venv/bin/alembic revision --autogenerate -m "message"          # nouvelle migration
.venv/bin/alembic upgrade head                                   # appliquer les migrations
.venv/bin/python -m pytest tests/ -q                              # lancer les tests
.venv/bin/python scripts/creer_utilisateur.py --email moi@exemple.fr   # créer un utilisateur
```

**Points d'attention à ne pas perdre en régénérant des fichiers :**
- `migrations/script.py.mako` a été modifié pour ajouter `import sqlmodel` (SQLModel ne l'ajoute pas automatiquement dans les scripts autogénérés, ce qui casse `upgrade()` sur les colonnes de type `AutoString`).
- Les tests utilisant une base SQLite en mémoire (`tests/conftest.py`) doivent utiliser `poolclass=StaticPool` — sans lui, chaque connexion ouvre une base `:memory:` vide différente.
- Dépendance de test `httpx2` (pas `httpx`) : Starlette `TestClient` a déprécié `httpx` en faveur de `httpx2`.
- `.env` est chargé via `python-dotenv` dans `app/config.py` (`load_dotenv`) — ne pas retirer cet appel, sans lui aucune variable de `.env` n'est lue (bug présent jusqu'à l'ajout de l'ingestion mail).
- Les datetimes persistées doivent être timezone-aware (`datetime.now(timezone.utc)`) — SQLModel/SQLAlchemy refuse désormais les datetimes naïves sur les colonnes `DateTime`.
- Le vrai `.env` du développeur contient de vrais identifiants Gmail (nécessaires à l'usage réel) : `tests/conftest.py` a un fixture `autouse` qui force `GMAIL_IMAP_ADRESSE`/`GMAIL_IMAP_MOT_DE_PASSE` à vide par défaut pour chaque test, sans quoi les tests dépendraient du contenu de `.env` et pourraient se connecter à la vraie boîte mail.
- `httpx2` (dépendance du `TestClient`, pas `httpx`) n'accepte que `Mapping[str, Any]` pour `data=` : pour envoyer un champ de formulaire répété, utiliser `{"champ": [v1, v2]}` (liste en valeur), **pas** une liste de tuples `[("champ", v1), ("champ", v2)]`.
- Avant d'appliquer une migration Alembic à la vraie base (`data/app.db`) : toujours `cp data/app.db /tmp/...` d'abord, tester la migration sur la copie, vérifier le schéma/les données, puis seulement l'appliquer au fichier réel, redémarrer le service (`sudo systemctl restart real-estate-manager`) et vérifier `journalctl -u real-estate-manager` avant de considérer la fonctionnalité terminée.
- **Un champ `Form(...)` (requis, sans défaut) envoyé avec une valeur vide (`""`) est traité par Starlette 1.10.0 comme un champ complètement absent**, pas comme une chaîne vide — que ce soit en `application/x-www-form-urlencoded` ou en `multipart/form-data` (vérifié empiriquement). FastAPI renvoie alors un **422 natif** avant même d'entrer dans la fonction de la route. Conséquence : le pattern `if X_parsee is None: raise ValueError("... obligatoire")` présent sur de nombreuses routes (dates/périodes requises) est du **code structurellement mort** — cette branche n'est jamais atteignable via une vraie requête HTTP sur un champ `Form(...)` sans défaut. Elle resterait utile seulement si le champ passait un jour à `Form("")` (optionnel avec défaut vide). Les tests sur ces champs doivent donc s'attendre à **422**, jamais à 400, pour une valeur vide — voir les tests `*_date_vide_est_rejetee_proprement` / `*_periode_vide_*` dans `tests/test_routers/`.
- **Un test de couverture peut révéler un vrai bug** : en écrivant le test "locataire_id inexistant" pour `occupation_creer` (`app/routers/unites.py`), on a découvert qu'une `Occupation` était créée et committée **avant** la validation des `locataire_ids`, laissant une occupation orpheline (active, sans aucun locataire) en cas de 404 — ce qui bloquait silencieusement toute future attribution de l'unité (faux 409 "déjà occupée"). Corrigé en validant tous les locataires avant de créer l'occupation.
- `coverage.py` sous Python 3.11 ne trace pas de façon fiable certaines lignes immédiatement après un `except courtes:` ou en fin de fonction multi-lignes, même quand elles sont bel et bien exécutées (vérifié manuellement sans l'outil, hors pytest) — ne pas chasser à tout prix un "Missing" isolé d'une seule ligne si une exécution manuelle confirme que le code tourne ; c'est un artefact de l'instrumentation, pas un vrai trou.
- **Ajouter une valeur à un enum Python existant** (ex. `TypeBien`) déclenche une migration même si SQLite n'impose aucune vraie contrainte sur la colonne : Alembic compare la longueur VARCHAR implicite (`max(len(valeur) for valeur in enum)`) entre le schéma réel et le modèle Python, donc toute nouvelle valeur plus longue que les précédentes fait apparaître un faux "modify_type". Le correctif est un `op.batch_alter_table(...).alter_column(..., type_=sqlmodel.sql.sqltypes.AutoString(length=<longueur exacte de la nouvelle valeur>))` — vérifier la longueur exacte en Python (`len("MA_VALEUR")`) plutôt que de la deviner, et confirmer avec `alembic check` qui doit revenir à "No new upgrade operations detected" après coup.
